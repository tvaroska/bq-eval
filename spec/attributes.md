# Telemetry Attribute & Event Contract

> Standard-first attribute and event names read by Silver adapters. Use OpenTelemetry and cloud semantic conventions wherever a standard exists, preserve `outcome.*` from `EVAL-P11`, and place only attributes outside those standards in the `bq_eval.*` namespace (`ADR-015`).

## Rules

1. **Standards first:** Never invent a `bq_eval.*` key when an OpenTelemetry (`v1.45+`), OpenTelemetry GenAI (`v0.1+`), MCP, A2A, or cloud semantic convention already defines the concept.
2. **Missing stays empty:** If an application omits an attribute, Silver leaves the column `NULL` and counts it where tracked. Silver never fabricates defaults.
3. **One-way trust on self-claims:** An application's claim that it failed (`bq_eval.app_failed = true`) is published as a fact and counted against the turn by evaluation. A claim that it passed or was verified is never read. Compliance pins (`protected_block_sha256`) are verified against authoritative `skill_registry`, never self-certified. A row in `events` is authoritative only when it sits in the system-of-record copy of `workflow_events`.
4. **Restricted identity & business keys:** Raw `user.id`, `bq_eval.tenant_id`, and `outcome.subject` appear **only** in `silver_restricted` (`traces`, `tool_calls`, `events`, `outcomes`). The open twins (`silver_open`: `traces_open`, `tool_calls_open`, `events_open`, `outcomes_open`) omit all raw ids, text, business keys, argument hashes and file digests (`ADR-038`). Out-of-band KMS-HMAC hashes (`user_id_hash`, `tenant_id_hash`, `hmac_key_version`) belong to the [clouds extension](clouds.md).
5. **Verified comes from provenance:** No attribute can make a fact verified. Silver derives `identity_attested`, `args_hash_attested` and `traffic_type_attested` from where the record landed, and binds an application's identity the same way ([silver.md](silver.md#provenance-and-verified-facts), `ADR-034`, `ADR-040`).
6. **Columns are bounded (`ADR-039`, `ADR-045`):** An attribute becomes a typed Silver column when Silver or a Gold add-on formula/gate computes, joins, or filters on it; pure slice-only attributes (~30 prompt, agent-version, MCP, A2A, cloud-residency, and evaluation-score keys) travel as registered keys of the `labels` `JSON` column ([`sql/silver/schema/labels_registry.json`](../sql/silver/schema/labels_registry.json); open-safe keys only in `*_open`).

## 4. Canonical `events` View Taxonomy

Every row in Silver `events` (`sql/silver/schema/events.json`) is filtered by `event_time` in `[from_time, to_time)`, keyed by `(source_class, event_id)` (`span:<trace_id>:<span_id>` for closing/guardrail spans; `_AllLogs.insert_id` for `gen_ai.evaluation.result` logs), and carries `event_id`, `event_time`, `event_type`, `source_system`, `source_class`, `is_authoritative`, `trace_id`, `span_id`, `response_id`, `outcome_id`, `linked_outcome_id`, `outcome_status`, `state_transition_to`, `conversation_id`, `trace_owner_app_id`, `action_id`, `nudge_id`, `control_id`, `control_layer`, `control_action`, `action_args`, `approved_args_sha256` / `committed_args_sha256` (RFC 8785 JCS over `action_args`), `approved_expires_at`, `feedback_reason`, `duplicate_count`, `conflict_count`, `user_id`, `tenant_id`, `actor_id`, `payload_json`, and `labels` (`JSON`). `events_open` omits `action_args`, both hashes, `payload_json`, `user_id`, `tenant_id`, and `actor_id` (while retaining `linked_outcome_id`, `outcome_status`, `state_transition_to`, `approved_expires_at`, `nudge_id`, `control_id`/`control_layer`/`control_action`, and `feedback_reason`).

- **Outcome lifecycle (`outcome.*`):** `outcome.opened`, `outcome.linked` (`linked_outcome_id` lifted from `payload_json` and projected below `events_open` to `outcome_links` for M:N correlation in `UC7`), `outcome.acknowledged`, `outcome.rejected`, `outcome.ticket_created`, `outcome.waiting_customer`, `outcome.customer_replied`, `outcome.escalated`, `outcome.parked_for_approval`, `outcome.approved`, `outcome.denied`, `outcome.resumed`, `outcome.closed` (carrying `outcome_status`).
- **Actions, guardrails, state & governance:** `action.committed` (authoritative SoR write commitment), `guardrail.intervention` (structured with `control_id`, `control_layer`: `gateway | dlp | model_armor | app_rule`, and `control_action`: `block | redact | shadow` — distinct from `bq_eval.app_failed`; platform-verified when it sits on a platform-class span or in the platform copy of `workflow_events`, unverified when it comes from an application's own rule), `state.transition` (`state_transition_to`: `Guide | Answer` in `UC9`), `model.approved` (authoritative MRM release gate in `UC5`/`UC10`), `handling.started` / `handling.ended`, and domain verification events (`ci.verified`, `postmortem.verified`, `recommendation.accepted`, `recommendation.rejected` — authoritative **only** when written to the system-of-record copy of `workflow_events`, never when sent to the application/IDE copy; `ADR-034`, `ADR-045`).
- **SDLC coding events (`UC8`):** `code.accepted`, `code.reverted`, `test.failed`, `sast.blocked`, `pr.abandoned` (emitted via IDE/CI webhooks into the application copy unless emitted by a gated CI release service into the SoR copy).
- **Operational workflow human signals (blind SME calibration labels belong strictly to Gold):** `feedback.thumbs_up`, `feedback.thumbs_down` (with `feedback_reason` and optional `nudge_id`, deduplicated per `(trace_id, nudge_id, user_id)` by latest `event_time`), and `review.routed`, `review.accepted`, `review.corrected`.
- **Authority rule:** `is_authoritative = true` exclusively for rows written to the system-of-record copy of `workflow_events`; `source_class` (`system_of_record | platform | application`) is set by the copy or trace store a row landed in (`ADR-034`).

## 5. The Input Table for Records That Are Not Spans

One append-only table, `workflow_events`, partitioned by `DATE(event_time)` and clustered by `(outcome_id, action_id)`, with 20 fixed columns: `event_id`, `event_time`, `event_type`, `source_system`, `trace_id`, `span_id`, `response_id`, `outcome_id`, `conversation_id`, `action_id`, `nudge_id`, `control_id`, `control_layer`, `control_action`, `action_args`, `approved_expires_at`, `user_id`, `tenant_id`, `actor_id`, `payload_json` (holding registered keys `linked_outcome_id`, `outcome_status`, `feedback_reason`, and `state_transition_to`, `ADR-045`).

- **Three isolated copies (separate IAM & VPC-SC perimeters):** One copy may be written only by systems of record (approval service, ticketing, mail gateway, committing SoR, CI/MRM release service) over private connectivity inside a dedicated SoR perimeter; a second copy may be written only by platform controls that produce no span of their own (gateway, safety filter, identity proxy, tool proxy); the third copy is for application/IDE telemetry. Table location decides `is_authoritative` and `source_class` (`ADR-034`).
- **Standard adapters:** A deployment maps custom systems via a view; for DevAI (`UC8`), BQ Eval documents a standard **Git/CI-to-`workflow_events` Adapter** schema emitting `ci.verified` (to the SoR copy when run by an isolated CI release service), `sast.blocked`, `code.accepted`, `code.reverted`, and `pr.abandoned`.
- **Approvals and committed writes:** Both rows carry `action_args`, the object `{"tool_name": ..., "args": ...}` with the arguments exactly as the tool received them (approvals may add an `approved_expires_at` TTL). Silver computes `approved_args_sha256` and `committed_args_sha256` from it with one RFC 8785 (JCS) implementation; writers never supply pre-computed hashes on `workflow_events` (`ADR-041`).
- **Repeated event ids:** Within one copy the first row by `event_time` with an `event_id` counts. A later row with the same id and the same content is counted as a duplicate; one with different content is counted as a conflict (`ADR-041`).
