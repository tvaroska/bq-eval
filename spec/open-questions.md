# Open Questions

> What is undecided or still requires live-environment verification. Settled decisions live in [silver.md](silver.md), [gold.md](gold.md), [clouds.md](clouds.md), [capacity.md](capacity.md), and the design notes; this note tracks only what remains open or empirically unverified.

## Column lists & exact schema files

Exact BigQuery column schemas (`sql/silver/schema/*.json`) and the registered `labels` key catalog (`sql/silver/schema/labels_registry.json`) are committed under `sql/silver/schema/` (`ADR-045`, closing missing-ID span counts, column-vs-`labels` placement, `payload_json` lifting for `linked_outcome_id`/`outcome_status`/`feedback_reason`, and bounded-lookback `outcomes` with `extends_outside_window`). Remaining Gold/extension items:

- **Decided (`ADR-034`):** when the root span and a platform-class span elsewhere in the trace carry different user ids, Silver does not choose; which id is the requester is Gold's rule. Open with that rule: the rule itself (leaning: the platform-class id, because it is the verified one), and whether Silver then publishes that id beside the root span's (leaning: yes, Gold cannot read it otherwise).
- **Decided (`ADR-033`):** Multi-trace/map-reduce outcomes default to worst-chunk `min_model_confidence` alongside `final_model_confidence`.
- Whether per-BU KMS-HMAC `user_id_hash`/`tenant_id_hash` (`hmac_key_version`, `ADR-028`/`ADR-031`) should also populate `silver_open` in single-cloud deployments. Leaning: yes, so per-user cost reads stay in `silver_open` without raw ids while preserving RTBF crypto-shredding separation.

## Tests on the trace store (live probes & remaining perimeter checks)

Five Cloud Trace (`_AllSpans` linked BigQuery dataset) behaviors were tested live:

- **Access — verified on standard projects; VPC-SC + multi-region CMEK still untested:** Both an authorized view and an authorized dataset (`targetTypes: ["VIEWS"]`) patch onto linked `_AllSpans` and `_AllLogs` datasets and allow a zero-privilege service account to query rows (`HTTP 200`, direct=`403`). Over Shape-3 storage, plain GCS external tables fail (`400 accessDenied`), whereas **BigLake tables (`WITH CONNECTION`)** succeed (`HTTP 200`). **Still untested (P0 live probe):** cross-project Authorized Datasets (`_AllSpans`, `_AllLogs`) and per-BU `bqcx-*` BigLake Connections across **locked-down VPC-SC perimeters + `US`/`EU` multi-region CMEK** and multi-project landing zones.
- **Row policies, measured 2026-11-25:** a row access policy cannot be created on the linked trace table (`is a linked dataset`), on a view over it, on a view over an ordinary table (`only supported on BigQuery tables, BigLake external tables, and BigQuery tables for Apache Iceberg`), and the statement does not accept a table function (`was not found`). So the per-unit row policies of `ADR-031` cannot protect `light` objects built over the trace table. Two ways that worked the same day: a row filter inside the function keyed on the caller (`SESSION_USER()` against an entitlement table), and a row policy on a stored table read through a function; in both the owner saw only unit `a` and a second account only unit `b`. **Decided (`ADR-044`):** in `light` each restricted function keeps only the caller's business units, read from an entitlement table, and row policies stay for what is stored (`workflow_events`, by-reference payload tables, reference tables, a stored span base). **Open:** how the entitlement list is fed, since the filter sees the caller's own account and not group membership (known limit, not tested). Leaning: synced from the directory. Also open: whether per-tenant separation (`UC9`) uses the same filter. Leaning: yes, as tenant rows in the same list.
- **Three copies of `workflow_events` in separate perimeters, not testable in one project:** perimeters are set at organisation level around whole projects, so three isolated copies mean three projects, and a query across perimeters needs an egress rule on one side and an ingress rule on the other (documentation search, not tested). **Open:** whether Silver's `events` object reads across perimeters through such rules, or the three copies share one perimeter and differ only in who may write.
- **Pruning & single-pass — verified with two traps:** Inside-horizon `start_time` filters cut scanned bytes **`37x`** vs. outer filters past `GROUP BY`. Expressing `spans` as `UNION ALL` over `_AllSpans` scanned `_AllSpans` **`2x`**, so shape routing runs in one single `SELECT` pass. **Still untested (P0 live benchmark):** the design-only high-volume profile, a stored text-free span base side by side with bounded `enterprise` `MERGE` (with static target `DATE(start_time)` partition pruning and `max_bytes_billed` / `INFORMATION_SCHEMA.JOBS` slot circuit breakers) at multi-PiB scale.
- **Arrival — verified:** Spans landed in `_AllSpans` in `13.8s–21.6s` after OTLP `HTTP 200` (`receive_time - end_time` `50–113 ms`).
- **Size — hard-rejects at `65,533` bytes (no truncation):** Exact measured per-attribute string cap is **`65,532` bytes** (`HTTP 200`); `65,533+` bytes hard-rejects the span (including inside mixed `HTTP 200` `partialSuccess` batches and span `events`), requiring Shape 3 for large payloads and reverse `action.committed -> tool_calls` checks for regulated writes.
- **Trace state — verified:** W3C `traceState` (`ot=th:...`) is preserved verbatim in `_AllSpans.trace_state`.
- **Read windows, measured 2026-11-25 (`ADR-035`):** a table function of a from-time and a to-time over `_AllSpans`, with the read margin inside and membership decided after grouping, scanned `42.7 KB` for one day, with literal arguments and with query parameters alike, the same as plain SQL with the filter inside, against `1.63 MB` for the whole table; it returned the same `639` traces as plain SQL. A function over a function and a fixed-window wrapper view kept the pruning. A window read from a table at query time did not prune (`1.63 MB` processed), so a window has to arrive as literals or parameters.
- **Access through functions, measured 2026-11-25:** a table function authorized as a routine on the linked trace dataset returned rows to an account with no access to `_AllSpans` (`HTTP 200`; before authorization, on a plain view and on the table itself `Access Denied`), and a view over that function needed no authorization of its own. Authorizing a whole dataset for views did not cover its functions, and an authorized view did not pass its authorization on to a function it calls (`Access Denied` both). Replacing the function with `CREATE OR REPLACE` removed its authorization while the entry stayed listed; applying the entry again restored it. So a function that reads Bronze directly has to be authorized itself, and again after each redeploy. Not tested: a function over an authorized function for a reader without Bronze access; `_AllLogs`.
- **Writer provenance, measured on recorded traces (`ADR-034`):** `_AllSpans` has no column that records who wrote a span, so the writer class has to come from the landing place. The server-set `apphub` column was empty on all `38,859` spans, while `34,803` carried a self-declared `apphub.application.id` resource attribute. The environment attribute appears under its older name `deployment.environment` on `23,783` spans and under `deployment.environment.name` on none, so the second identity path has to read both (`ADR-040`). **Still untested:** a gateway's spans in a separate landing place joining an application's spans by trace id; it needs a second project, because the trace store keeps one bucket per project (documentation search, not tested).
- **Root facts, measured (`ADR-037`):** of `8,716` Cloud Run traces only `49` had a parentless span; `8,665` of the other `8,667` had only server-kind top spans, whose parent is the runtime's front end, and `2` had other orphans. A "no parent" definition of root would mark `99.4%` of these traces rootless. The same picture appears at every service hop: of `25,969` application server spans none has its parent in another service, and `11,169` have a parent that is not stored, because the cloud runtime's own span sits between caller and callee. An orphan of server kind therefore shows no loss, and a lost span whose only children are server spans in another service stays invisible. Of the `1,580` parentless spans, `1,555` were the cloud runtime's own request spans (no instrumentation scope, no span kind, a `/component` label of `HTTP load balancer` or `AppServer`) and `25` carried no SDK resource attributes (probe spans sent by hand; `24` checked by name). No deployed application emitted a parentless span. **Decided (`ADR-037`):** the root is the first span, by start time, that an application emitted; the cloud runtime's own spans do not count. Measured on `8,856` traces with application spans: that span never had an application span above it and was never tied; `6,144` traces had one top application span and `2,712` had two to eight, so "top-most" alone does not pick one. While a trace is still arriving, its entry span may not be in the store yet. Turns, measured: `499` of `9,494` traces hold an agent, model-call or tool span (`447` a model call); where the runtime's request span is stored and starts first, it precedes the first application span by `17 ms` at the median and up to `53 s`.
- **Read margin, measured (`ADR-035`):** trace length was `244 ms` at p50, `18.8 s` at p95, `54.1 s` at p99 and `406 s` at most; a start-time filter cut `6` of `170` traces at the start of a busy 30-minute window.
- **Span kinds and tokens, measured (`ADR-036`, `ADR-042`):** `35,708` spans (`92%`) carried no GenAI operation. `1,045` spans carried a token attribute and `924` reported a count above zero; the `121` zeros include all `99` tool spans that carried the attribute. The operations Silver lists as model calls (`chat`, `generate_content`, `embeddings`, legacy `call_llm`) covered `702` of the `924` spans but only `35%` of their input tokens; the rest sat under application-specific operation names. Only `8` spans carried content in an accepted shape.
- **Token spans inside token spans, measured (`ADR-042`):** `22` spans that report tokens enclose `50` others: `2` legacy ADK wrappers equal to their inner call, and `20` application spans of which `7` equal the sum of their inner calls and `13` report less. None reports more than its inner spans. Counting both adds `66,360` input tokens (`1.1%`) here and doubles them in the legacy ADK format. **Decided (`ADR-042`):** the innermost span that reports tokens is the model call, and an enclosing span is not counted again.
- **Duplicates, measured (`ADR-042`):** `791` `(trace_id, span_id)` keys appear twice, with the same attributes and different arrival times: `753` are runtime request spans and `38` are application spans from one load run. `dropped_attributes_count` and `dropped_events_count` were zero on every span.
- **Sampling, measured (`ADR-043`):** no application span carried a sampling probability, in trace state or as an attribute.
- **Scan size, measured (`ADR-035`):** a query that reads the trace table through five subqueries processed `6.1 MB` against `4.8 MB` for one, so bytes do not grow with the number of references, while slot time grew `5.5x`. A filter on arrival time processed the same bytes as a filter on start time, and a window passed as query parameters the same bytes as literals. A table function behaves the same (read windows, measured).

## Settle time, read margin & session inactivity cutoffs

Exact default values for the read margin around a window, `settle_buffer`, `merge_lookback_days`, `outcome_lookback_days`, and Gold's bounded `session_inactivity_hours` cutoff are deployment settings to be tuned from live span arrival skew and scan-cost measurements.

## Hash equality

Tested live in BigQuery: `TO_JSON_STRING(PARSE_JSON(...))` fails int-vs-float equality (`100` vs. `100.0` / `1e2`, `0` vs. `0.0` / `-0.0`), so both execution-time `bq_eval.args_sha256` and Silver SQL fallback hashing use deterministic **RFC 8785 (JCS)** normalization (with a payload-byte guard before SQL UDF invocation).

## Offline runner

Measured locally on 2026-11-25, with toy SQL and the tools already in the repository. The offline engine the tests use (SQLite) refuses table functions as written (`5` of `5` attempts). With a rewrite that inlines each function body and substitutes the arguments, `80` lines on top of the repository's translator rules, `19` of `19` checks passed, including a function over a function, a view over a call and a window relative to the current time; a `58`-line version still failed some of them. One early version returned `0` of `240` rows without an error, because a timestamp literal reached the engine as a number; the expected-rows check has to catch that. Canonical JSON plus SHA-256 as a registered function passed `27` of `27` checks (`88` lines, standard library only). One run of define, three calls and `1,000` hashes over `10,000` spans took `0.12`–`0.15 s`, and `0.5`–`0.6 s` for the whole process, against the `5 s` target. Not tested: that BigQuery and the offline engine return equal rows and equal hashes; real Silver SQL. Offline the hash is a second implementation, so the shared test cases of `ADR-041` apply to it too.

## Limits of content by reference

- Standalone `execute_tool` spans in traces with zero model calls have no uploaded model-message payload; aborted turns must emit tool errors and execution-time `bq_eval.args_sha256` directly on `execute_tool` spans.
- **Measured live (`200` tiny JSONL files, `374 KB`):** dynamic `_FILE_NAME` and dynamic Hive `e.dt = s.span_dt` joins scanned `100%` of files (`~80–125 ms` slot/file), whereas static Hive literal predicates (`WHERE dt = DATE '...'`) pruned reads. Shape 3 therefore mandates BigLake Connections + static Hive date/hour predicates + micro-batched Parquet/Iceberg at scale. **Measured 2026-11-25:** a table function over a BigLake table on Hive-partitioned files read `2` of `4` files for a one-day window given as literals or as query parameters (`2.01 MB` against `4.03 MB` for all), the same as plain SQL; with the window read from a table at query time it read all `4` although `3` were needed.

## Settled architecture items (`ADR-029`–`ADR-033`)

- **Hub region & residency (`ADR-031`):** Multi-region (`US` or `EU`) is the default Hub topology with strict per-domain location/CMEK alignment (never mix `US` and `us-east4` in one query domain); non-hub sovereign/single regions act as spokes via the Hub Transfer Port.
- **Regulated WORM & RTBF (`ADR-031`):** Regulated snapshots export to PII-free **GCS Bucket Retention-Lock + CMEK** archives (not BigQuery tables alone) paired with per-subject crypto-shredding DEKs for RTBF. Open: shipping the exact Terraform/DDL archival template.
- **Fast local/CI gates (`ADR-032`):** Sub-5s DevAI PR gates and offline optimizer sweeps run through the **Local/CI Eval Runner Port** (`CI_ONLY`), never polling BigQuery.
- **Cross-cloud skew (`ADR-031`):** Hub views flag split traces whose remote spoke `transfer_watermark_utc` has not yet advanced as `remote_fragment_pending = true`.
- **Outcome status (`ADR-029`):** `rejected | denied` added alongside `guardrail.intervention`. Open: syncing new enum values into cross-repo `EVAL-P11`.

## A step that fits no shape

Decided (`ADR-036`, `ADR-042`): the shape is decided by content and the kind of a span by its operation name, and a span that reports tokens above zero is a model call whatever that name is. A span with no GenAI operation and no tokens is an ordinary span: kept, counted, not flagged. `spans` keeps one row per `(trace_id, span_id)`, the latest arrival, and counts the rest. A model or tool call without content is kept in the text-free objects with a content-missing fact and is not scored (`ADR-036`); in the recorded traces no deployed service sends content in an accepted shape, so all `918` of its token spans are of that kind. Still open: a span whose operation name is outside the conventions and that reports no tokens, such as the `631` recorded `invoke_node` spans. Leaning: keep it and count it. Also open: a tool span that reports tokens above zero, which the recorded traces do not contain. Leaning: it stays a tool call and its tokens also appear as a model call.

## Clouds extension (remaining live benchmarks)

Architecture is decided in `ADR-028`, `ADR-031`, and `ADR-046` ([clouds.md](clouds.md), [design/clouds.md](../design/clouds.md)). **Still unbenchmarked / untested live:**
- **Regional vs. `US`/`EU` Cross-Cloud Interconnect binding:** Verify live whether a `US`/`EU` multi-region BigQuery Cross-Cloud Connection can bind a regional Service Directory / Cross-Cloud Interconnect endpoint or requires a single-region (`us-east4` / `europe-west3`) Hub domain like Lakehouse Runtime Catalogs.
- **Azure private transport parity:** Verify private non-internet routing for Azure ADLS Gen2 across BigQuery Cross-Cloud Connections and Borderless Lakehouse (AWS CCI is documented; Azure ADLS Spark/CCI parity has documented gaps).
- **Routine authorization over 4-part `P.C.N.T` federated catalogs (`ADR-035`, `ADR-044`):** Verify live whether BigQuery `CREATE OR REPLACE TABLE FUNCTION` authorized routines enforce zero-direct-catalog caller isolation over 4-part `project.catalog.namespace.table` federated Iceberg tables (since federated/cross-cloud tables disallow BigQuery Row Access Policies).
- **CMEK `restrictNonCmekServices` cache-disablement & `object_storage_stats` accounting:** Measure cross-cloud bytes scanned (`object_storage_bytes_read` vs. `cache_bytes_read` in `INFORMATION_SCHEMA.JOBS_BY_PROJECT.object_storage_stats`) when `constraints/gcp.restrictNonCmekServices` auto-disables Intelligent Caching, confirming once-per-settled-window Gold materialization bounds remote egress despite `0`-byte pre-flight dry runs.
- **Spoke & transfer benchmarks:** Staged `Hub Transfer Port` throughput (`STS -> Hub GCS -> LOAD DATA`) at scale, Spark/Trino spoke conformance against `M18-1`/`ADR-041` JCS fixtures, AWS Bedrock VPC `In-Cloud Judge Port` latency/cost, cross-cloud KMS-HMAC rotation drill, and recorded multi-cloud fixtures.
