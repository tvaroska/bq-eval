# Silver

> The objects the core publishes and the rules they follow. Every add-on is written against this note and nothing else.

## Published objects

Every Silver object is published through **one logical SQL contract** over Bronze sources and the reference tables. The default (`light`) deployment publishes each object as a table function of an explicit time window, with no stored data and no scheduled job ([Read windows](#read-windows), `ADR-035`); in these notes "view" means such an object, and fixed-window views are thin wrappers. The high-volume (`enterprise`) profile is design only. `spans` is the internal single-pass base; Gold add-ons read the six published views (plus the `outcome_links` bridge view for M:N correlation) built on top of it (`model_calls`, `tool_calls`, `events`, `trace_payloads`, `traces`, `outcomes`, `outcome_links`).

Four views hold text, raw ids, or business keys next to other columns. Each has an open twin without them: `traces_open`, `tool_calls_open`, `events_open`, and `outcomes_open` (see [Access](#access)). The open twins carry no hashes of arguments and no file digests, only a repeat number per trace ([Hashes](#hashes-rfc-8785-jcs)). Non-LLM time-series or raw GPU inference workloads use a separate sibling metric table rather than polluting LLM token semantics in `model_calls`.

## Reference tables & Two-Speed CI/CD Registry Port

| Table | One row per | Holds |
|---|---|---|
| Application list (`app_registry`) | application (and optional `agent_id`), versioned by `effective_from` / `effective_to` | Telemetry identities that map to it (an App Hub id, or a service name plus environment), the landing places its spans must arrive in, owner, business unit, environment, `risk_tier` (`RL-1`..`RL-5`), `payload_profile` (`ephemeral_sample \| regulated_worm`), `sampling_mode` (`full \| sampled`), `barrier_domain` (MNPI / information-barrier clearance domain), `runtime_lane`, and optional MRM governance (`mrm_model_id`, `validation_expiry_date`). |
| Tool list (`tools`) | application and tool (versioned by `effective_from` / `effective_to`) | Factual capability flags only: `writes_state` (system-of-record mutation), `modifies_workspace` (local dev/sandbox file edit — never triggers SoR HITL SoD checks), `executes_code`, `sends_external_reply`, `returns_pii`, `creates_ticket` (approval thresholds and rules live in Gold). |
| Skill list (`skill_registry`) | application, skill, and version (versioned by `effective_from` / `effective_to`) | Authoritative pinned `skill_sha256` and immutable `protected_block_sha256` compliance-block digest (so automated optimizers and applications never self-certify compliance hashes). |
| Entitlement list (`unit_entitlements`) | reader account and business unit | Which business units a reader may see in `silver_restricted`; every restricted function filters by it (`ADR-044`). How it is fed is open ([open-questions.md](open-questions.md)). |

- **Mandatory SCD-2 for regulated workloads:** SCD-2 validity windows (`effective_from`, `effective_to`; `NULL` end means active) joined at span/trace time are **mandatory** for `RL-1`–`RL-3` and `regulated_worm` workloads so edits never rewrite historical audits (non-regulated `RL-4`/`RL-5` apps may leave windows open). Gold additionally snapshots reference values with every stored result.
- **Two-Speed CI/CD Dual-Registry Ingestion Port (`ADR-032`):** To support high-velocity (`300x/day`) GitOps delivery without sacrificing `SR 11-7` control, Silver defines a GitOps **CI/CD Dual-Registry Ingestion Port** syncing manifest artifacts (`agent-card.json`, `toolspec.json`, `SkillRevision`) into `app_registry`, `tools`, and `skill_registry`:
  - *Fast lane (`RL-3`–`RL-5` additive changes):* Automated GitOps sync registers new low-risk applications, read-only/workspace tools, and candidate skills.
  - *Governed lane (`RL-1`/`RL-2` & capability downgrades):* Any `RL-1`/`RL-2` promotion, `skill_registry.protected_block_sha256` change, or tool-capability downgrade (`writes_state`, `returns_pii`, or `sends_external_reply`: `true -> false`) requires dual-signed `CODEOWNERS` / MRM approval — never an automated application write.
- **Federated Registry Sync (dark-agent detection):** Reconciles `app_registry` against cloud agent registries (`AWS`, `GCP`) so Gold flags both uninstrumented registered agents ("dark agents" emitting zero telemetry) and unregistered emitting workloads.

Capacity pools, capacity allocations, and the model allow-list belong to the [capacity and governance extension](capacity.md). A user directory is not a Silver table; Gold cost joins whatever directory the deployment provides.

## Rules

### Telemetry comes in at most three shapes

Silver reads three shapes of telemetry in BigQuery SQL and no others. Every shape carries content, on the step or by reference ([shapes.md](shapes.md#content-is-required)). The shape says how content is read; the kind of a span (model call, embedding, tool call, retrieval, memory, agent, other) is read from its operation name, and a span that reports tokens above zero is a model call whatever that name is (`ADR-042`). Spans with no GenAI operation and no tokens are kept and counted as ordinary spans, never flagged. A model or tool call without content is kept: it stays in the text-free objects with a content-missing fact (`content_missing`), has no text row, is not scored by evaluation, and is counted by cost and monitoring (`ADR-036`). Non-conforming frameworks, coding SDKs, and custom gateways normalize upstream through the Bronze / OTel Collector Adapter Port ([shapes.md](shapes.md)). Standard OpenTelemetry names, `EVAL-P11` `outcome.*` keys, and minimal `bq_eval.*` attributes are specified in [attributes.md](attributes.md).

### Reference data enriches and flags; it never drops

Every trace gets its owner, unit, environment, `risk_tier`, and `barrier_domain` from `app_registry`, every tool call gets its flags from `tools`, and every skill gets its pinned digests from `skill_registry`. A missing lookup is published as a fact (`unregistered_app`, `unregistered_tool_count`, `unregistered_skill`). Every row stays; each Gold add-on decides what a fact means.

### Counts, facts, types, and nullability

Silver does not decide whether a trace passed. It publishes counts and facts only, and each add-on defines its own pass ([gold.md](gold.md)). Missing values stay `NULL` and are counted — never defaulted:
- **Structured and list columns use BigQuery `JSON` (never `ARRAY`)** so `NULL` (absent) stays distinct from `[]` (present and empty) across BigQuery queries (`ADR-045`).
- **Child-set counts** (`tool_call_count`, `duplicate_span_count`, `caller_retry_count`, `trace_count`, `duplicate_count`, `conflict_count`, etc.) are `0` when the counted set is empty; `traces` token totals are `NULL` when `model_call_count = 0`; `is_authoritative`, `is_closed`, `is_turn`, `has_root_span`, `extends_outside_window`, and `content_missing` (`false` on `embeddings`) are never `NULL`; provenance/bound booleans (`identity_attested`, `traffic_type_attested`, `args_hash_attested`, `app_identity_bound`) are `NULL` when their subject (`user_id`, `traffic_type`, `args_sha256`, `trace_owner_app_id`) is `NULL`, else `TRUE`/`FALSE` (`ADR-045`).
- An application's self-reported failure (`bq_eval.app_failed = true`) is published as a fact; a self-reported pass or "outcome verified" is never read.

### Columns and labels

A value gets its own typed Silver column when Silver **or a Gold add-on formula/gate** computes, joins, or filters on it. Pure slice-only attributes (~30 prompt, agent-version, MCP, A2A, cloud-residency, and evaluation-score keys) travel in one `labels` `JSON` column registered in `sql/silver/schema/labels_registry.json` (`ADR-039`, `ADR-045`; open-safe keys only in `*_open`). Exact schemas for all objects live under `sql/silver/schema/`.

### Provenance and verified facts

A record's writer class is set by where it landed, never by what it says about itself (`ADR-034`).

| Class | Lands in | Examples |
|---|---|---|
| `system_of_record` | the copy of the input table only systems of record may write | approvals, committed writes, releases |
| `platform` | a trace store, or a copy of the input table, only the deployment's own controls may write | gateway, identity proxy, tool proxy, safety filter |
| `application` | everything an application can write | agent spans, application events, feedback |

`identity_attested`, `args_hash_attested` and `traffic_type_attested` are true only for facts read from platform-class records, and `is_authoritative` only for system-of-record rows (including `ci.verified`, which is authoritative only when written by a CI release service to the system-of-record copy of `workflow_events`, never from the application/IDE copy; `ADR-034`, `ADR-045`). An attribute that claims to be verified is ignored. A deployment that needs verified facts gives gateway and tool-proxy spans a landing place applications cannot write to. The trace store has no column that records who wrote a span (measured), so the landing place is the only source of the class ([open-questions.md](open-questions.md)). The cloud runtime's own spans (its load balancer and front end, carrying no instrumentation scope) keep `source_class = NULL` and are not platform-class.

An application's identity is bound the same way (`ADR-040`): `app_registry` lists the landing places an application's spans must arrive in, and an identity claimed from anywhere else is published as not bound (`traces.app_identity_bound = false`; `NULL` when `trace_owner_app_id` is `NULL`). Where a rule depends on the tier, Gold treats unbound and unregistered applications as the strictest tier. Inside one landing place identity stays self-declared.

### Row rules

- **3-principal identity, structured OBO claims & provenance.** Every trace records `trigger_principal` (`human | event | automated`), `agent_principal`, requester `user_id` / `tenant_id` (plus optional `act_chain` `JSON`), and structured OBO attestation (`identity_attested`, `auth_method`, `issuer`, `aud` per RFC 8787, `delegation_chain_hash`). **Silver publishes the `user_id` it saw**, the root span's `user.id` (`ADR-025`), with `user_id_source` (`platform | application`) naming the class of span that carried it. `identity_attested` is true only when a platform-class span carried it (`NULL` when `user_id` is `NULL`), derived from provenance ([Provenance](#provenance-and-verified-facts)) — never read from an attribute. Whether an unverified id counts is decided in Gold per risk tier (`ADR-034`). Because the root is the first application span, an application has to stamp `user.id` on its entry span or `user_id` stays empty. Disagreeing `user.id` spans are counted (`user_id_conflict_count`). For single-valued trace attributes that may sit on several spans (`tenant_id`, `conversation_id`, `traffic_type`, `skill_sha256`), precedence is **platform gateway span -> root span -> earliest call span (`start_time, span_id`)** (`ADR-045`). Where a platform-class span elsewhere in the trace carries a different user id, Silver does not choose: which id is the requester is decided in Gold (`ADR-034`, [open-questions.md](open-questions.md)).
- **Ownership (`trace_owner_app_id` precedence over central proxies).** Where a shared multi-tenant LLM gateway or proxy sits at the trace root, caller/desk entitlement attribution (`bq_eval.caller_app_id` recorded on the platform-class gateway span) takes precedence over the proxy's own service name so multi-tenant gateway traffic never collapses under one proxy app ID. Otherwise the application of the root span owns the trace; `participating_app_count` is recorded. A span's application is found through `app_registry`: `apphub.application.id` first, else `(service.name, COALESCE(deployment.environment.name, deployment.environment))`; no match stays unregistered (`ADR-040`, `ADR-045`).
- **Agent of a call.** A model or tool call belongs to the agent named on the call itself, else the nearest enclosing agent span (`invoke_agent`).
- **Span deduplication & tool pairing.** `spans` holds one row per `(trace_id, span_id)` per landing place (platform winning cross-place clashes), the latest arrival, and the rest are counted as duplicates (`ADR-042`, `ADR-045`). A server tool span folds into a client tool span only when it is that span's child (or linked via `mcp.session.id` through a proxy-mediated W3C parent chain — never by name and arguments). In legacy ADK Format 1 traces where `call_llm` wraps a child `generate_content` span with duplicate token usage, the pair folds into one `model_calls` row keeping the inner `generate_content` span's ID, times, tokens, and `operation_name` while lifting `gcp.vertex.agent.llm_request`, `llm_response`, and `session_id` conversation fallback from `call_llm` when absent on the child (`ADR-042`, `ADR-045`). The general rule: where a span that reports tokens encloses another one, only the innermost is a model call (`is_model_call = true` alongside operation-based `span_kind`), and the enclosing span's tokens are a rollup that is never summed.
- **Turn prompt, context & stateful delta turns.** `turn_prompt` is the last input before the first model output of the turn, whatever its role. `turn_context` holds an ordered `JSON` array of the turn's `tool_calls` results (`execute_tool`, `retrieval`, `memory_*`, plus `gen_ai.retrieval.documents` where present) tagged with `span_id`, `tool_name`, `operation_name`, and `tools` flags (`ADR-020`, `ADR-045`). For stateful APIs carrying `previous_interaction_id`, `prior_history` stays `NULL` in Silver (without miscounting missing history), while Gold performs bounded cross-turn session-context reconstruction where required ([gold.md](gold.md#1-evaluation-add-on)).
- **Reply text & multi-output steps.** `turn_output` is the arguments of the last tool call with `sends_external_reply = true`, else the last model output under the root agent that asked for no tool. Multi-part structured outputs and per-nudge outputs remain inspectable in `step_outputs` (`JSON`) keyed by `nudge_id` where emitted.
- **Model-call ids, models and retries.** `model_calls` keeps the client request id and the provider response id in two columns, and the requested and the responding model in two columns; nothing is merged. `caller_retry_count` is, for one model call, the number of directly preceding model calls in the same trace (ordered by `start_time, span_id`), by the same agent for the same `request_model`, that ended with HTTP `429` (`0` when none). A split of cache-write tokens by lifetime is not published until an attribute carries it (`ADR-039`, `ADR-045`).
- **Confidence & escalation rollups.** `model_calls` retains per-call `model_confidence`. `traces` exposes `final_model_confidence` (last call reporting confidence), and `outcomes` publishes **both `min_model_confidence` (default for multi-trace/map-reduce safety gating) and `final_model_confidence`**. `escalated` is `true` when any call has `cascade_tier = 'escalation'` or an `outcome.escalated` event exists (`false` otherwise).

### Outcomes, events & M:N correlation

- `outcomes(from_time, to_time)` publishes one row per `outcome.id` with at least one trace or event inside `[from_time, to_time)`, aggregating its traces and events across `[from_time - outcome_lookback_days, to_time + read_margin)` and setting `extends_outside_window = true` when activity lies outside `[from_time, to_time)` (`ADR-045`). Business unit comes from `outcome.owner` resolved in `app_registry`, else the earliest member trace's `trace_owner_app_id`, else `'__unowned__'`.
- `events(from_time, to_time)` and `outcome_links(from_time, to_time)` filter on `event_time` in `[from_time, to_time)`. `events` lifts `linked_outcome_id`, `outcome_status`, `feedback_reason`, and `state_transition_to` from registered `workflow_events.payload_json` keys (keeping the 20 fixed `workflow_events` columns unchanged), and keys rows on `(source_class, event_id)` (`span:<trace_id>:<span_id>` for closing/guardrail spans; `_AllLogs.insert_id` for `gen_ai.evaluation.result` logs).
- Each trace carries at most one primary `outcome.id` on spans (`multiple_outcome_ids = true` when multiple appear). Workloads requiring M:N correlation (e.g., one SRE investigation spanning multiple incidents in `UC7`) link secondary outcomes via `outcome.linked` rows, projected through `outcome_links` (`silver_open`, built below `events_open` so `events_open` omits `payload_json`).
- Waiting times are not summed in Silver, and Silver never declares an outcome verified.

### Text & Shape 3

A turn is a trace with at least one agent, model-call or tool span (`traces.is_turn`); other traces, such as page loads, are kept and are not turns (`ADR-037`). One turn is one `trace_id` (`gen_ai.conversation.id` links multi-turn sessions; `outcome.id` links multi-trace cases); `traces.user_turn_count` above 1 marks a trace that holds more than one user turn (`0` when `is_turn = false`, `1` on content-missing turns). `trace_payloads` splits `prior_history` from this turn's delta (`turn_prompt`, `turn_context`, `turn_output`, `step_outputs`, `media_uris`), plus 5 `*_read_whole` booleans (`prior_history`, `turn_prompt`, `turn_context`, `turn_output`, `step_outputs`; `NULL` when the corresponding column is `NULL`, `true` inline, `false` on missing Shape-3 ref).

In Shape 3 (content by reference), storage sits behind a **BigLake table (`WITH CONNECTION`)** with schema `(dt DATE, hr STRING, ref_uri STRING, payload JSON)` over Hive date/hour partitions (`dt=YYYY-MM-DD/hr=HH/`, micro-batched Parquet/Iceberg preferred at scale) with static window predicates following `gen_ai.input.messages_ref` and `gen_ai.output.messages_ref` (keeping `system_instructions_ref` and `tool_definitions_ref` as addresses; `ADR-045`) — never a plain external table and never an unpruned dynamic `_FILE_NAME` join. **Open twins (`*_open`) never scan restricted Shape-3 payload buckets.**

### Hashes (RFC 8785 JCS)

`args_sha256`, `approved_args_sha256`, and `committed_args_sha256` use **RFC 8785 (JCS)** over `{"tool_name": <tool_name>, "args": <arguments>}`. The hashed object is the tool name plus the arguments exactly as the tool received them when it ran; the approval service stores that same object, and the model's raw text is not used (`ADR-041`). The tool-side hash names its source in `args_hash_source` (`proxy | silver | application | none`): the execution-time `bq_eval.args_sha256` of a platform-class tool-proxy span (`args_hash_attested = true`); Silver's own hash of inline `arguments` on the tool span (`args_hash_attested = false`); an application `execute_tool` span's `bq_eval.args_sha256` when neither proxy hash nor inline arguments exist (`args_hash_attested = false`, `ADR-045`); or `none` (`args_sha256 = NULL`, `args_hash_attested = NULL`). It is never computed from the model's message, and a write without an attested tool-side hash (or authoritative commit match) cannot pass Gold's approval check. Every implementation must pass one shared set of test cases that is part of the contract. The open twins never carry these hashes or file digests: both `tool_calls` and `tool_calls_open` publish `repeat_number` (dense rank per trace of `(tool_name, args_sha256)` in order of first `(start_time, span_id)`, `NULL` when `args_hash_source = 'none'`), and `tool_calls_open` omits `args_sha256` plus the 8 digest/business-key/code-summary columns (`ADR-038`, `ADR-045`); repeats across an outcome are counted in Gold from the restricted views. Silver's own hashing uses a deterministic BigQuery UDF guarded by a `65,532`-byte ceiling so malformed/oversized inline JSON never exhausts query slots.

### Completeness

- The root of a trace is the first span, by start time, that an application emitted; a gateway or proxy at the entry counts as an application here, the cloud runtime's own spans (its load balancer and front end) do not (`ADR-037`). `traces.root_span_id` names it, and `has_root_span` is false only when no application span is stored. While a trace is still arriving its entry span may not be stored yet, so the root is final once the trace has settled. `trace_start_time` is the start of the earliest stored span, with `trace_start_writer` (`runtime | application`) saying who wrote it.
- Silver publishes separately why a trace is incomplete: `missing_parent_count` (a parent that should be in the store is not, for example a span rejected for size); `entry_parent_outside` (the root span has a parent that is not stored: the caller or the runtime's front end); `exceeds_read_margin` (the trace is longer than the margin read around the window); and the last span arrival time, from which Gold tells a trace that is still running. A server or consumer span whose parent is not stored is normal at the entry of a trace and at every service hop, so it is not counted as a missing parent; any other orphan is. A lost span whose only children are server spans in another service therefore stays invisible to these facts; the reverse commit check covers writes (measured, [open-questions.md](open-questions.md)).
- `traces` records `tool_call_count`, `mutating_tool_call_count`, `workspace_edit_count`, `unregistered_tool_count`, `content_missing_call_count`, `user_turn_count` and `duplicate_span_count` whatever the root facts say.
- `traces` reads `sampling_probability` from W3C `trace_state` else `bq_eval.sampling_probability`; **missing stays `NULL`, never `1.0`**; Gold does not scale applications the registry declares `full` (`ADR-043`).
- Gold never silently drops traces without a root that contain tool calls or `writes_state` mutations; its safety alert uses `missing_parent_count` only, once the trace has settled. Gold also reconciles authoritative `action.committed` rows back against `tool_calls` to catch `65,533+ B` OTLP dropped spans.

### Read windows

BigQuery does not push outer filters past `GROUP BY` (`37x` scan penalty measured live).

- **Explicit window (`light`, `ADR-035`):** every published object is a table function of a from-time and a to-time, with no stored data. The window filter sits inside `spans`, with matching static Hive `dt` predicates on BigLake Shape 3.
- **Whole turns only:** a trace belongs to the window in which its first span starts. Silver reads a margin before and after the window so no member trace is cut; a trace longer than the margin is flagged (`exceeds_read_margin`).
- **What is repeatable (`ADR-035`):** a window has settled when its end, the read margin and the settle time have passed. From then on the same call returns the same telemetry columns. Registry columns are repeatable only where validity windows exist; elsewhere they are as known at read time, and Gold stores the values it used. `events` and `outcomes` are as known at read time. Fixed-window views (for example the last 2 hours) are thin wrappers over the functions.
- **Measured:** a window passed as function arguments, as literals or as query parameters, limits scanned bytes as plain SQL with the filter inside does; a window read from a table at query time does not. A function that reads Bronze directly is authorized on it by itself, and again after every redeploy ([open-questions.md](open-questions.md)). How `outcomes`, which can span days, relate to a window is open.
- **High-volume profile (`enterprise`, design only, `ADR-035`):** not decided. The candidate stores only a typed, text-free copy of spans, appended as they arrive, and keeps the published objects as functions on top, so both profiles run the same SQL and text is never copied. The earlier candidate, one incrementally merged table per published object, stays on record until a side-by-side test chooses: it runs every `5–15` minutes in an isolated slot reservation over `(receive_time_watermark - settle_buffer .. now)` into `DATE(start_time)`-partitioned tables clustered by `(COALESCE(trace_owner_app_id, '__unowned__'), trace_id)`. **Mandatory partition-pruning contract (`ADR-031`):**
  1. Every `MERGE` statement **must include a static target partition-prune predicate** (`target.partition_date >= DATE_SUB(CURRENT_DATE(), INTERVAL merge_lookback_days DAY)`) in the `ON` clause so late-arriving or midnight-straddling spans never rewrite multi-TiB historical partitions.
  2. `outcomes` and Gold session rollups enforce explicit bounded lookback windows (configurable `outcome_lookback_days` / `session_inactivity_hours`) rather than scanning full history.
  3. All compaction jobs enforce `max_bytes_billed` and reservation slot circuit-breakers ([gold.md](gold.md#shared-rules)).

### Access (multi-project split datasets, split SAs & RAPs)

Restricted and open objects live in **two physically separate datasets** (`silver_restricted` and `silver_open`, supporting multi-project Bronze/Silver/Gold landing-zone separation) with independent IAM and location-matched CMEK keys:

- `silver_restricted` holds `trace_payloads`, `traces`, `tool_calls`, `events`, and `outcomes` (including `outcome.subject`, text, arguments/results, raw `user_id`/`tenant_id`), with business units separated so multi-LOB payloads are never co-mingled across readers: in `light`, each restricted function keeps only the rows of the caller's business units, read from `unit_entitlements` keyed on the caller (`ADR-044`, mapping `NULL` business units to `'__unowned__'` for admin/audit entitlements so unregistered or unowned rows are never silently lost, `ADR-045`), and **row access policies (RAPs)** protect what is stored (`workflow_events`, by-reference payload tables, reference tables, a stored span base). Row policies cannot be attached to the linked trace table, to views or to table functions (measured, [open-questions.md](open-questions.md)).
- `silver_open` holds `traces_open`, `tool_calls_open`, `events_open`, `model_calls`, `outcomes_open` (zero `outcome.subject`), and `outcome_links` — zero text, zero raw ids, zero business keys, zero argument hashes or file digests, zero joins to restricted Shape-3 payload buckets.
- In `light` mode, the functions that read Bronze `_AllSpans`/`_AllLogs` directly are **authorized on it one by one** (measured: authorizing a dataset covers its views, not its functions, and replacing a function drops its authorization), fixed-window views over them need none, and `silver_restricted` reads Shape 3 strictly via a per-BU-scoped **BigLake Connection** with VPC-SC egress/CMEK verification.
- In the design-only `enterprise` profile, compaction would run under **two separate least-privilege service accounts** (a restricted-tier SA writing `silver_restricted` and a text-free open-tier SA writing `silver_open` from text-free projections) so one compromised job never bridges both tiers.

| Reader | May read |
|---|---|
| Gold Evaluation add-on (in-cloud checks & judges) | `silver_restricted` (subject to the per-unit caller filter), `silver_open`, and SCD-2 reference tables (`app_registry`, `tools`, `skill_registry`) |

## One implementation & Local/CI Runner Port

The SQL that ships for BigQuery is the single implementation of Silver. Offline runs — both repo verification gates and the first-class **`< 5s` Local/CI Eval Runner Port** (`CI_ONLY`, [layers.md](layers.md)) — execute that exact SQL through a deterministic translator over local OTLP trace fixtures. When the translator and BigQuery disagree, BigQuery is right.

## Proof

Each object has a committed BigQuery schema file (`sql/silver/schema/*.json` plus `sql/silver/schema/labels_registry.json`, `ADR-045`) and fixed recorded-trace inputs with exact expected rows. No telemetry column depends on the time of reading once its window has settled; registry columns, `events` and `outcomes` are as known at read time ([Read windows](#read-windows)). Verification runs offline on every gate and on live BigQuery in build/release pipelines.
