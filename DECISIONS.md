# Architectural Decisions (`DECISIONS.md`)

## ADR-001: Dedicated Showcase Separation & Cross-Repo Boundaries (`bq-eval` vs. `agent-evals` vs. `capacity`)
- **Context**: Combining a runnable BigQuery evaluation and FinOps software toolkit with deep Financial Services Model Risk Management (`SR 11-7`, `SR 26-2`) regulatory playbooks, 60-paper academic literature surveys, and GSU capacity sizing/gateway actuation in a single repository created an onboarding cliff for product and platform engineers.
- **Decision**: Split responsibilities across three loosely coupled repositories bridged by versioned wire contracts:
  1. **`bq-eval` (`tvaroska/bq-eval`)**: Standalone **BigQuery-Native Enterprise Agent Evaluation, Observability & Cost Management Showcase** owning dual-path telemetry ingestion (`BQAA` `agent_events` & OTel `_AllSpans`), progressive `Step 1 -> Step 2 -> Step 2.5 (Agentic Skill) -> Step 3` BigQuery SQL views, conditional Rogan-Gladen / Gwet's `AC2` calibration, multi-provider USD cost & `CPVO` aggregation, and `v_capacity_hourly_burndown_export`.
  2. **`agent-evals`**: Owns the normative cross-repo evaluation standards (`EVAL-P01`–`EVAL-P11`), regulated banking Model Risk Management (`SR 11-7`, `SR 26-2 / OCC 2026-13`) playbooks, `RAIR`/`RSR`/`60-40` audit gates, academic literature compendiums, and cross-workspace compliance auditing (`eval-audit`).
  3. **`capacity`**: Owns GSU/GPU sizing optimization, sub-minute 3P burst physics, gateway YAML/CEL routing policies, idle pool reallocation UIs, and live `FOCUS 1.2` billing actuation consuming `bq-eval` hourly burndown exports (`allocate_focus_hourly_chargeback`).
- **Rejected Option**: Monolithic single-repo bundling MRM regulatory playbooks, live gateway actuation, and the BigQuery telemetry/SQL showcase together (steep onboarding cliff and blurred build/compliance boundaries).

## ADR-002: BigQuery as Pure Execution Engine & Progressive Step 1 → Step 2 → Step 2.5 → Step 3 Onboarding
- **Context**: Requiring product teams to provision 7 tables, register in App Hub, or set up human labeling panels on Day 1 creates a steep setup curve. Meanwhile, both live production traffic and offline/staging test runs already emit OpenTelemetry traces.
- **Decision**:
  1. **Source Is Always Traces (`otel_spans` + `trace_payloads`)**: Workload agents emit standard OpenTelemetry `gen_ai.*` spans (`0` custom evaluation or FinOps SDK code).
  2. **Step 1 (`0` New Tables, No Skill Needed — `sql/core/step1_trace_views.sql`)**: Predefined static SQL views (`v_step1_trace_waterfall`, `v_step1_trace_eval`, `v_step1_cost_per_outcome`) run directly over existing traces (`gcp.apphub.application.id` used when present, automatic fallback when absent) with built-in default Gemini rates (`<=200K` and `>200K` cliffs) to deliver waterfalls, `$0` SQL checks, and **Day-1 Cost per Application, Business Unit & Outcome**.
  3. **Step 2 (`1` Rubric Table / CSV, `0` Result Tables, No Skill Needed — `sql/core/step2_rubrics.csv` + `sql/core/step2_stateless_eval.sql`)**: Add a single `rubrics` table (mounted from a Cloud Storage CSV or created as a native BigQuery table seeded with 8 canonical 4-point rubrics, including `EVAL-P10` contradiction grounding and PII perturbation invariance) and run static `AI.GENERATE_TABLE` evaluations on **100% of traces** or a **10% sample** without saving results.
  4. **Step 2.5 (Agentic Skill — `skills/bq-eval/SKILL.md`)**: Introduce the Agentic Skill when teams want plain-English authoring of new 4-point rubrics, custom trace slices (**5% sample**, **only the last 1 hour of traces**, error/SLA tail), or custom domain Step-1+ SQL checks.
  5. **Step 3 (`2` Tables: `rubrics` + `eval_results` — `sql/core/step3_saved_results.sql`) & Open Extensions (`sql/core/ddl.sql`)**: Persist verdicts into `eval_results` (`eval_run_id`) for `0%` negative-flip regression gates and longitudinal trends, while keeping `~100` blind human spot-checks (`sme_labels`), `app_registry`, `model_pricing_catalog`, and `FOCUS 1.2` capacity exports open as optional enterprise extensions.
- **Rejected Option**: Requiring upfront 7-table schema provisioning and human calibration panels before showing Day-1 waterfalls/CPVO, or pulling warehouse trace tables out into a Python-only evaluation loop.

## ADR-003: Hybrid & Multi-Cloud Coverage via Keyless WIF Collector & `COALESCE` Resolution
- **Context**: In-GCP workloads (`Agent Engine`, `Cloud Run`, `GKE`) receive automatic `gcp.apphub.application.id` resource attributes via `telemetry.googleapis.com`, whereas external workloads (`AWS EKS`, `Azure AKS`, on-prem Kubernetes, local dev) run outside GCP metadata servers and invoke multi-provider models.
- **Decision**:
  1. External agents emit plain local OTLP (`:4317`) to a cluster OpenTelemetry Collector authenticating keylessly via **Workload Identity Federation** (`sts.googleapis.com`).
  2. Both BigQuery SQL (`sql/core/step1_trace_views.sql`, `sql/core/views.sql`) and Python (`bq_eval/core/contract/otel.py`) resolve application identity via `COALESCE(gcp_apphub_application_id, JSON_VALUE(attributes, '$."gcp.apphub.application.id"'), JSON_VALUE(attributes, '$."apphub.application.id"'), 'unregistered_app')`, so any workload without App Hub registration surfaces directly under `'unregistered_app'`.
- **Rejected Option**: Distributing static GCP service-account key files to multi-cloud workloads (credential sprawl) or silently trusting self-reported framework app strings ahead of infrastructure-stamped App Hub IDs.

## ADR-004: Fail-Closed Rogan-Gladen Calibration, Two-Mode `Rule 0` Routing & Dual IRR
- **Context**: Scoring deterministic `Rule 0` failures (`rule0_pass = FALSE`) with an LLM wastes judge tokens, and pooling `100%`-sampled failure tails with `5–10%`-sampled healthy canaries in $\hat{p}_{\text{judge}}$ overweights deterministic errors by `10x–20x`. Conversely, diagnostic sweeps occasionally want LLM root-cause tags on failing tails, while defaulting `judged_samples == 0` to `1.0` makes unjudged apps appear `100%` accurate.
- **Decision**:
  1. **Two-Mode `Rule 0` Judge Routing**: Routine Step-2/Step-3 semantic scoring skips `$0` deterministic rejects (`WHERE step1_pass = TRUE` in `v_step2_trace_rubric_prompts`, `v_bqaa_eval_turn_filtered`, and `build_ai_generate_table_judge_sql(..., include_rule0_failures=False)`), sending only `5–10%` canary + tool-error/SLA-tail passes (`tool_error_count > 0 OR trace_latency_ms > sla_latency_ms`) to the LLM judge. Optional diagnostic root-cause runs inspect `Rule 0` failures via `v_step2_all_trace_rubric_prompts` or `build_ai_generate_table_judge_sql(..., include_rule0_failures=True)`.
  2. **Conditional Prevalence Calibration & 100% Billing**: `v_agent_eval_and_finops_summary` estimates $\hat{\theta}_{\text{RG}} = \hat{P}(\text{Semantic Pass} \mid \text{Rule 0 Pass})$ strictly over `WHERE rule0_pass = TRUE` judged traces (excluding any diagnostic `Rule 0` failure judge calls) while billing `100%` of judge runs (`autorater_judge_usd`) to the application's evaluation overhead.
  3. Evaluate `calibrated_pass_rate` and `cost_per_verified_outcome_usd` fail-closed to SQL `NULL` / Python `None` in BigQuery views and `evaluate_traces_in_sqlite()` whenever `judged_samples == 0` (`UNJUDGED`), any population stratum is unjudged or unmatched, `judged_samples < 10`, reference counts `(tp + fn) < 5` or `(tn + fp) < 5`, or Youden's $J = \widehat{\text{TPR}} + \widehat{\text{TNR}} - 1 \le 10^{-6}$ (or Wilson-adjusted $J' \le 10^{-6}$) (`UNCALIBRATED`), while direct `rogan_gladen_calibrate()` and `stratified_rogan_gladen_calibrate()` raise `ValueError`.
  4. Enforce `AND judge_pass IS NOT NULL` on paired SME calibration rows, apply `StratPPI` population stratum weighting across `ERROR_OR_SLA_TAIL` vs. healthy canary strata (failing closed if any populated stratum has zero judged rows), and report boundary-safe **Lang & Reiczigel (2014) Eq. (6)/(7)/(16)/(17)** 95% confidence intervals (with center shift $\Delta P$ and Kish effective $n$ at boundaries) in both BigQuery SQL, SQLite, and Python alongside prevalence-robust **Gwet's AC2** (`compute_gwet_ac2()`).
- **Rejected Option**: Unconditionally running an LLM judge on every trace (`10–20x` cost), pooling `rule0_pass = FALSE` traces into $\hat{\theta}_{\text{RG}}$ (selection bias), or defaulting unjudged/degenerate calibration outputs to `1.0`.

## ADR-005: Portable, Customer-Agnostic Repository Hygiene
- **Context**: Showcase repositories must be safe to clone, run in isolated Cloud Build containers, and share externally without leaking customer identifiers, internal shortlinks, or workstation paths.
- **Decision**: Enforce automated AST and text hygiene gates (`tests/test_repo_hygiene.py`, `tests/test_isolation_guard.py`) blocking internal codenames, internal shortlinks, hardcoded workstation home directory paths, local file URI schemes, `.github/workflows/`, escaping relative Markdown links, and forbidden model SDK or upward-layer imports in deterministic core modules.
- **Rejected Option**: Ad-hoc manual code-review checklists without automated CI AST/regex hygiene gates (regressions slip into fixtures, SQL comments, and docs).

## ADR-006: Outcome-Adjusted FinOps, `>200K` Burndown Cliffs & `NFR = 0.0%` Pareto Right-Sizing
- **Context**: Raw token dashboards hide whether an agent succeeded, miss the `>200K` long-context PT burndown cliff (`2.0x` input / `7.5x` output), ignore `1/N` round-robin prefix-cache dilution, and cannot prove whether downgrading a model breaks working cases.
- **Decision**: Center FinOps on **USD Cost per Verified Outcome** (`bq_eval/finops/engine/spend.py`), separating `production_inference`, `conflict_escalation`, `agent_gym_eval`, and `autorater_judge` spend, evaluating `>200K` burndown cliffs (`compute_weighted_burndown_tokens()`) at the span level before `GROUP BY trace_id`, quantifying **Eval FinOps ROI** (`compute_eval_finops_roi()`, `90–95%` judge savings), and gating model right-sizing on `fabrication_rate == 0.0%` (`compute_pareto_frontier()`).
- **Rejected Option**: Trace-level averaged token reporting without `>200K` span cliff checks or accuracy-unconstrained model downgrades (hides tail cost explosions and silent regressions).

## ADR-007: Capacity & `FOCUS 1.2` Two-Pool Chargeback Actuation Bridge
- **Context**: `8x5` business-hours applications active `40h/week` (`23.8%` duty cycle) are penalized `3x` when charged for `24x7` idle Provisioned Throughput commitments, while overnight idle PT GSUs sit unused.
- **Decision**: Export hourly regional/BU burndown (`v_capacity_hourly_burndown_export`), compute **FinOps Foundation `FOCUS 1.2` Two-Pool Chargeback** (`allocate_focus_two_pool_chargeback()`: `Utilized PT` billed to BUs vs. `Unutilized Idle` billed to central platform), and schedule batch `AI.GENERATE_TABLE` evaluations into overnight idle PT valleys at `$0.00` marginal commitment cost (`plan_off_peak_eval_schedule()`).
- **Rejected Option**: Uniform `24x7` flat PT allocation across tenants (unfairly penalizes `8x5` workloads and misses free overnight eval valleys).

## ADR-008: Dual-Path Capture (`Light Capture BQAA` + `Full Capture OTel`) -> Single Evaluation & FinOps Engine
- **Context**: Individual ADK and LangGraph developers adopt 3-line **BigQuery Agent Analytics (`BQAA`)** (`BigQueryAgentAnalyticsPlugin` / `BigQueryCallbackHandler` -> `agent_events` via Storage Write API) to avoid multi-resource OpenTelemetry setup and capture candidate tool schemas for `AI.EVALUATE_AGENT`, whereas multi-service and multi-cloud enterprise fleets require server-stamped App Hub attribution and W3C `baggage` propagation via native OpenTelemetry (`telemetry.googleapis.com` -> `_AllSpans`).
- **Decision**:
  1. Keep repository slug `bq-eval` and retitle to **BQ Eval & FinOps**, positioning it as the unified evaluation, calibration, and FinOps execution engine over **Light Capture (`BQAA`)**, **Full Capture (`OTel` `_AllSpans`)**, or **Hybrid `UNION ALL`** (`sql/core/bqaa_adapter_views.sql` + `bq_eval/core/engine/bqaa.py`).
  2. Enforce `ADR-003` strict `'unregistered_app'` fallback on `v_bqaa_otel_spans` (`gcp_apphub_application_id` and `outcome_owner` resolve strictly from `custom_metadata` App Hub keys or `_AllSpans` join, never collapsing into self-reported `adk.app_name` or `agent`), deduplicate Storage Write API retries via `QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ...) = 1`, and support both **Engine A (`AI.GENERATE_TABLE`)** and **Engine B (`AI.EVALUATE_AGENT` via `v_bqaa_eval_turn_filtered`)** behind Step-1 `$0` SQL pre-filtering.
- **Rejected Option**: Requiring full OTel Collector + GCS payload buckets for single-developer ADK experiments, or maintaining disconnected evaluation/FinOps pipelines per ingestion lane.

## ADR-009: Offline SQLite Twin Behind Transpiled BigQuery Parity Tests (`F11`, Re-Confirmed `M12-7`)
- **Context**: `bq-eval` ships BigQuery SQL views (`sql/core/views.sql`, `sql/core/summary_views.sql`, `sql/core/step1_trace_views.sql`) for cloud execution alongside a local in-memory SQLite twin (`bq_eval/core/engine/sqlite_views.py` and `bq_eval/finops/engine/sqlite_capacity.py`, invoked by `evaluate_traces_in_sqlite()`, `bq-eval demo`, `bq-eval serve`, and `bq-eval capacity-export`). Transpiling BigQuery SQL into SQLite at runtime via `sqlglot` would promote `sqlglot` from a dev-only dependency into the runtime wheel, require maintaining custom runtime BigQuery-to-SQLite rewrite rules and aggregate UDFs (`APPROX_QUANTILES(...)[OFFSET(95)]`, `ARRAY_AGG(... ORDER BY ... LIMIT 1)[SAFE_OFFSET(0)]`, `SAFE_CAST(... AS BOOL)`), and widen the runtime attack/bug surface.
- **Decision**: Keep the hand-written SQLite twin as the minimal-dependency (`pydantic`-only) runtime engine for `demo`, `serve`, and `capacity-export`, and enforce mathematical and relational equivalence against the shipped BigQuery SQL through `sqlglot`-transpiled value-level parity tests (`F3` in `tests/test_sql_enterprise_views.py`, `tests/test_critical_paths.py`, `tests/test_sql_harness_and_views.py`, and `tests/test_sqlite_parity.py`, keeping `sqlglot` dev-only).
- **Re-Confirmed Upkeep Cost (`M12-7` / `M15-4`)**: After deleting the two unused SQLite view twins (`v_interaction_session_lineage`, `v_live_slo_and_429_breaches`) in `M12-6`, the runtime SQLite mirror surface is bounded to two modules (`bq_eval/core/engine/sqlite_views.py` and `bq_eval/finops/engine/sqlite_capacity.py`). Across `M13`–`M15`, all `48/48` shipped BigQuery views execute through the dev-only transpiled parity harness (`< 1e-12` numeric agreement on calibration, Lang & Reiczigel 95% CIs, cliff cache-write pricing, and CPVO). This bounded two-file maintenance cost is strictly cheaper and safer than shipping a runtime SQL transpiler in the wheel; the single-SQL-source alternative is formally closed.
- **Rejected Option**: Runtime `sqlglot` transpilation of `sql/core/*.sql` (adds a runtime dependency + custom SQLite/BigQuery emulator in production code and increases runtime surface area without removing the need to test BigQuery semantics).

## ADR-010: Bronze and Silver Core in BigQuery, Gold Add-Ons on Top
- **Context**: Two parallel trace view chains feed different add-ons, so the traces a judge scores and the population its scores are weighted against come from different SQL. The shared views price every span and fill defaults for missing values. Traces stored in another cloud arrive already computed and never join the others by trace ID. A hand-written SQLite copy mirrors the SQL (`ADR-009`), so every defect in the shared views is found and fixed twice.
- **Decision**: The core is Bronze (telemetry left in place) plus Silver: five published objects (`spans`, `requests`, `trace_payloads`, `traces`, `outcomes`) produced by SQL inside BigQuery, in the cloud where the data lives. Silver uses telemetry and shared reference data (application list, dedicated capacity, allowed models). It holds no prices and no judge results, leaves missing values empty, publishes one column per check, and trusts what an application says about itself only when it reports a failure. Gold add-ons (evaluation, monitoring, cost) read the published Silver objects and nothing below them; the cost add-on may also read `spans` with a date range. Requirements are in [`spec/`](spec/layers.md), design in [`design/`](design/bq-eval.md).
- **Supersedes `ADR-009` for Silver**: The shipped BigQuery SQL becomes the only implementation of Silver. Offline runs (demo, fast tests) execute that SQL through the translator, BigQuery is the authority when the two disagree, and the expected-rows check also runs on BigQuery in the build. Until that work ships, the code still follows `ADR-009`.
- **Rejected Options**: Keep one of the two existing chains (it prices spans and fills defaults). Compute other-cloud Silver in the hub (moves spans across clouds). Keep the SQLite copy of Silver (two implementations).
- **Consequences**: The translator becomes a dependency of the demo. A trace split across two clouds is judged on the part its home cloud can see. Evaluation of a trace has to run in the cloud that holds its text.

## ADR-011: At Most Three Telemetry Shapes, One Adapter View per Shape, Content by Reference
- **Context**: Agent frameworks write the same facts under different attribute names and in different places: on the step, in events on the step, in log records, or in storage. Reading every combination would mean tens of readers. Some content, such as long prompts and encoded files, is too large to rely on step attributes.
- **Decision**: Silver reads at most three shapes, where a shape is one family of names in one placement: ADK's own names on the step, the OpenTelemetry GenAI names on the step, and the OpenTelemetry GenAI names with content by reference (the step carries an address, the content sits in storage). Each shape has one adapter view inside BigQuery that maps to the common span columns. Each application is set up to produce one of the three; the setups are in [`spec/shapes.md`](spec/shapes.md). A new shape has to replace one of the three.
- **Rejected Options**: A reader per framework (tens of shapes). Rewriting telemetry in a collector before it is stored (the original is lost, a wrong mapping cannot be corrected, and applications that send straight to the trace store have no collector). One shape only (leaves ADK's older format and large content unread).
- **Consequences**: ADK's own shape has to be replaced when ADK removes its older trace format. Content by reference costs a join to an external table for every trace that is judged and adds a second retention period. Frameworks that cannot produce one of the three shapes convert before their data lands, or wait. What is still undecided is in [`spec/open-questions.md`](spec/open-questions.md).
